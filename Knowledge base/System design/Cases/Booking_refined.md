# Booking — System Design

Пример: сервис бронирования отелей наподобие Booking.com.

Главная особенность кейса — **согласованность бронирований**: нельзя продать последний свободный номер двум пользователям одновременно. Дополнительная сложность — согласование бронирования с внешней оплатой.

# 1. Functional Requirements (функциональные требования)

- Бронирование отелей гостями.
- Отмена бронирования.
- Добавление и удаление номеров администратором.
- Просмотр списка отелей и номеров.
- Поиск отелей по местоположению.
- Полнотекстовый поиск.

# 2. Non-functional Requirements (нефункциональные требования)

- **DAU** (Daily Active Users — активные пользователи за день): **30 000 000**.
- Количество отелей: **300 000**.
- **Availability** (доступность): **99,95%**.
- В среднем **1 бронирование в месяц** на пользователя.
- В среднем **10 просмотров отелей в месяц** на пользователя.
- Геораспределённости нет.
- Есть сезонность: зима/лето, условный множитель **×2**.
- Поиск отеля: **2–3 секунды**.
- Бронирование отеля: **2 секунды**.

> Время бронирования в 2 секунды разумно трактовать как время создания/резервирования заказа, а не полного завершения оплаты через стороннего провайдера. В лекционных заметках это отдельно не уточнено.

# 3. Data Model (модель данных)

Модели ниже перенесены из схемы. Названия полей сохранены.

## 3.1 Hotel

```text
hotel:
- hotel_id
- title
- description
- lat / lont
- admin_id
- ...
```

Информация об отеле, включая местоположение и владельца.

## 3.2 Room Type

```text
room_type:
- room_type_id
- hotel_id
- title
- description
- count
- price
- ...
```

Тип номера, его стоимость и общее количество номеров этого типа. `room_type.count` — общее количество, а не количество свободных номеров на конкретную дату.

## 3.3 Order

```text
order:
- order_id
- user_id
- hotel_id
- room_type_id
- count
- price
- created_at
- from_date
- to_date
- status (PENDING / WAITING PAYMENT / CANCELLED / BOOKED)
- ...
```

Заказ связывает клиента, отель, тип номера и период проживания. Статус отражает жизненный цикл бронирования.

## 3.4 Free Room Type

```text
free_room_type:
- hotel_id
- room_type_id
- count
- date
```

**Отдельная структура доступности номеров по датам.** Например, у отеля может быть 10 номеров типа Standard, но на 15 ноября свободно 3, а на 16 ноября — 1.

Для поиска доступности на интервале `[from_date, to_date)` проверяем, что **на каждую ночь** интервала хватает номеров. При бронировании уменьшаем соответствующие счётчики на все нужные даты.

> Интервальная проверка и обновление всех дат — уточнение реализации. На схеме указаны `date` и `count`, но алгоритм многодневного бронирования отдельно не расписан.

# 4. Capacity Estimation (расчёт нагрузки)

## 4.1 RPS

**Просмотры отелей:**

```text
RPS(read) = 30 000 000 × 10 / 30 / 86 400 ≈ 116 RPS
```

**Создание бронирований:**

```text
RPS(order) = 30 000 000 × 1 / 30 / 86 400 ≈ 11,6 RPS
```

**Сезонный пик ×2 (упрощённая оценка):**

```text
RPS(read, season) ≈ 232
RPS(order, season) ≈ 23
```

Это средние значения, умноженные на сезонный коэффициент, а не расчёт мгновенного пика. Кратковременные всплески могут быть выше.

## 4.2 Network Traffic (сетевой трафик)

В лекции отдельный расчёт трафика опущен из-за небольшого RPS. Точные значения зависят от размеров ответов поиска и изображений отелей.

# 5. Workload Characteristics (характер нагрузки)

## Consistency-heavy (высокие требования к согласованности)

Основная проблема — конкурентное бронирование ограниченного ресурса. Два клиента могут одновременно попытаться занять последний номер.

## Transaction-heavy (критичность транзакций)

Создание заказа и уменьшение доступности должны быть согласованы. В монолитном Hotel Service с общей PostgreSQL это можно сделать в **одной транзакции**.

## Read-heavy по числу запросов (преобладание чтения)

Просмотров примерно в 10 раз больше, чем созданий заказов. При этом **стоимость и критичность** операции бронирования значительно выше, чем у обычного чтения.

## External-dependency-sensitive (зависимость от внешней системы)

Оплата выполняется через стороннего провайдера. Его задержки, недоступность и повторные уведомления влияют на жизненный цикл заказа.

**Вывод:** при сравнительно небольшом RPS сложность кейса определяется согласованностью, конкурентными изменениями и обработкой сбоев, а не количеством вычислительных хостов.

# 6. API

```text
API (clients):
- ListHotels(params)
- ListRooms(params)
- CreateOrder(params)
- CancelOrder(params)
- ListOrders(params)

API (admins):
- CRUD for hotels
```

Клиенты и администраторы используют разные наборы API. Их можно логически разделить, даже если физически используется один API Gateway.

# 7. High-Level Design (верхнеуровневая архитектура)

![[систем_дизайн_booking.drawio.svg]]

## 7.1 API Gateway

Принимает запросы клиентов и администраторов, направляет их в Hotel Service. Логическое разделение Client API и Admin API позволяет применять разные правила авторизации и ограничения.

## 7.2 Hotel Service — монолит

В лекции предлагается **монолит**, поскольку нагрузка сравнительно невысока, а бронированию нужна строгая согласованность.

Hotel Service отвечает за:

- управление отелями и типами номеров;
- поиск и отображение доступности;
- создание и отмену заказов;
- резервирование и освобождение номеров;
- изменение статуса заказа после оплаты.

В схеме используется **PostgreSQL** для основной информации и **Elasticsearch** для поиска (включая полнотекстовый). Между PostgreSQL и Elasticsearch на схеме указан **CDC** (Change Data Capture — передача изменений из БД). Поисковый индекс является производным представлением данных и может обновляться с задержкой; окончательную доступность при бронировании проверяем в основной БД.

**Почему монолит полезен здесь:** изменение `order` и `free_room_type` можно объединить в одну транзакцию PostgreSQL без распределённой транзакции между несколькими бизнес-сервисами.

## 7.3 Free Room Type — предварительно подготовленная доступность

Наивный вариант — каждый раз анализировать историю заказов и вычислять, сколько номеров осталось свободными.

Вместо этого поддерживаем отдельную таблицу `free_room_type`, в которой уже рассчитано количество свободных номеров каждого типа на каждую дату.

Это **precomputation** (предварительный расчёт) / **materialized subset** (заранее подготовленное представление данных): ускоряем частые чтения ценой дополнительной работы при изменении бронирований.

Таблицу можно поддерживать при создании, отмене или истечении срока резерва. Для корректной работы обновление должно учитывать весь период проживания.

## 7.4 Как избежать двойного бронирования

**Race condition (состояние гонки):** два пользователя одновременно видят `count = 1` и пытаются забронировать последний номер.

Вместо отдельного чтения и последующего изменения выполняем **atomic conditional update** (атомарное условное обновление):

```sql
UPDATE free_room_type
SET count = count - 1
WHERE hotel_id = :hotel_id
  AND room_type_id = :room_type_id
  AND date = :date
  AND count > 0;
```

Проверяем число обновлённых строк: если `0`, свободного номера на эту дату нет. Для нескольких ночей все нужные обновления и создание заказа выполняются **в одной транзакции**; если хотя бы на одну дату номеров нет, транзакция откатывается.

Полезное ограничение:

```sql
CHECK (count >= 0)
```

**Важно:** счётчик не отменяет внутренние блокировки PostgreSQL. Он позволяет избежать опасной схемы `SELECT → проверка в приложении → UPDATE` и выразить проверку вместе с изменением в БД. Для многодневного интервала необходимо также учитывать возможные конфликты и deadlock (взаимную блокировку) при обновлении нескольких строк.

## 7.5 Payment Service и внешний платёжный провайдер

Упрощённый сценарий из заметок:

1. Клиент вызывает `CreateOrder` в Hotel Service.
2. Hotel Service создаёт заказ и резервирует номера в одной транзакции.
3. Заказ ожидает оплаты (`WAITING PAYMENT`).
4. Пользователь переходит на страницу внешнего платёжного провайдера.
5. Провайдер сообщает результат через **webhook** (HTTP-уведомление о событии) в Payment Service.
6. Payment Service передаёт результат в Hotel Service.
7. При успехе заказ становится `BOOKED`; при неуспехе резерв снимается, доступность восстанавливается.

**Уточнение:** нельзя держать транзакцию PostgreSQL открытой всё время, пока пользователь оплачивает заказ. Транзакция резервирования заканчивается раньше; затем статус заказа изменяется отдельной транзакцией по результату оплаты.

На схеме показан один Payment Service со сторонней платёжной системой. В старых заметках также упомянут **резервный платёжный провайдер** как возможное повышение отказоустойчивости.

## 7.6 Если разделить Hotel Service и Order Service: Saga

Владимир отдельно рассматривает усложнение архитектуры: если при росте нагрузки выделить Order Service и Payment Service, единой локальной транзакции для всех шагов уже не будет.

Можно использовать **Saga** (сагу — последовательность локальных транзакций с компенсирующими действиями):

```text
Создать заказ
    ↓
Зарезервировать номер
    ↓
Попытаться провести оплату
    ├── Успех → подтвердить бронирование
    └── Ошибка → отменить резерв и вернуть доступность
```

Это концептуальный сценарий; конкретный координатор саги и обмен сообщениями на лекционной схеме отдельно не детализированы.

Важно: компенсация — не общий `ROLLBACK` для всех сервисов, а **новая бизнес-операция**, которая исправляет ранее выполненное действие.

## 7.7 Репликация и отказоустойчивость

- Для PostgreSQL Hotel Service в заметках предлагается **синхронная репликация**, поскольку важна сохранность и согласованность бронирований.
- В заметках также упомянута репликация Kafka для варианта событийной архитектуры. На приложенной схеме основного монолитного решения Kafka не показана.
- Репликация повышает отказоустойчивость, но не заменяет корректную транзакционную логику бронирования.

**Нюанс:** синхронная репликация PostgreSQL сама по себе не означает, что чтение с любой реплики всегда даёт строгую согласованность. Для решения о бронировании нужно обращаться к авторитетному состоянию и выполнять конкурентное изменение транзакционно.

# 8. Corner Cases и интересные архитектурные решения

## 8.1 Два пользователя бронируют последний номер

Оба видят доступность, но только один успешно выполняет атомарное уменьшение `count`. Второй получает отказ. **Проверка доступности на экране не гарантирует наличие номера к моменту бронирования.**

## 8.2 Бронирование на несколько ночей

Номер может быть свободен в первую ночь, но занят во вторую. Недостаточно уменьшить один счётчик: проверяем весь интервал дат и обновляем его атомарно в рамках одной транзакции.

## 8.3 Пользователь начал оплату, но не завершил её

Резерв не должен занимать номер бесконечно. Нужен срок действия неоплаченного заказа (**reservation timeout** — время жизни резерва) и операция освобождения доступности после истечения срока. Это дополнение к лекционному сценарию.

## 8.4 Webhook пришёл дважды

Платёжный провайдер может повторить уведомление. Обработка должна быть **idempotent** (идемпотентной): повторный webhook не должен дважды переводить статус или возвращать `count` два раза.

## 8.5 Оплата прошла, но ответ потерялся

Нельзя автоматически считать платёж неуспешным и повторять списание: возможно, деньги уже списаны. Нужны идентификатор платёжной операции, проверка её статуса и идемпотентность запросов к провайдеру. Это дополнительный эксплуатационный нюанс.

## 8.6 Отмена бронирования

При отмене нужно возвращать доступность только если резерв ещё удерживается и ещё не был освобождён ранее. Переходы статусов должны предотвращать двойной возврат номеров.

## 8.7 Доступность в поиске устарела

Elasticsearch или другое поисковое представление может отставать от PostgreSQL. Поиск показывает предварительную доступность, а окончательная проверка выполняется при создании заказа в основной БД.

## 8.8 Синхронная репликация не бесплатна

Подтверждение записи может ожидать реплику, увеличивая **latency** (задержку) и влияя на доступность записи при отказе реплики. Это компромисс, а не универсальное решение.

## 8.9 Почему не всегда нужны микросервисы

При небольшой нагрузке и тесно связанных изменениях (`order` + `free_room_type`) монолит позволяет использовать одну транзакцию. Разделение на сервисы добавит сетевые вызовы, саги, компенсации и новые сценарии отказов.

# 9. Важные выводы из кейса

1. **Согласованность важнее RPS:** даже 10–20 бронирований в секунду могут конкурировать за один и тот же номер.
2. **Подготовленное представление доступности** ускоряет чтения, но требует корректного обновления при каждом бронировании и отмене.
3. **Atomic conditional update** защищает ограниченный ресурс от двойного резервирования.
4. **Локальная транзакция монолита** проще распределённой координации нескольких сервисов.
5. **Оплата — отдельный асинхронный бизнес-процесс:** webhook, таймауты, повторы и компенсации нужно учитывать явно.
6. **Saga** помогает координировать локальные транзакции после разделения сервисов, но увеличивает сложность.
7. **Репликация** повышает отказоустойчивость, однако не заменяет инварианты, транзакции и идемпотентность.
