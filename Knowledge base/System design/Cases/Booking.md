# СТАРЫЕ ЗАМЕТКИ
В этом кейсе интересны четыре архитектурные идеи:

- разделение API клиентов и арендодателей;
- отдельное хранение availability (доступности);

- резервный payment provider (платёжный провайдер).

# 1. Разделение API клиентов и арендодателей

У системы есть два принципиально разных типа пользователей:

- клиенты;
- арендодатели / владельцы отелей.

У них разные сценарии использования системы.

## Client API (API клиента)

Например:

- поиск отеля;
- просмотр доступных номеров;
- создание бронирования;
- оплата бронирования.

## Owner API (API арендодателя)

Например:

- управление отелем;
- управление номерами;
- изменение доступности;
- изменение информации об отеле.

Поэтому API можно логически разделить:

Client
   ↓
Client API Gateway
   ↓
...

Owner
   ↓
Owner API Gateway
   ↓
...

При необходимости можно использовать и два отдельных API Gateway.

Главная идея:

> Если разные типы клиентов имеют сильно отличающиеся сценарии
> использования системы, их API можно разделить.

---

# 2. Отдельное представление Availability (доступности)

## Проблема

Представим, что у нас есть большая таблица всех номеров.

Нам постоянно необходимо отвечать на запрос:

> Какие номера сейчас доступны для бронирования?

Наивный подход — каждый раз искать свободные номера среди всех номеров.

Например:

Rooms
----------------
Room 1   FREE
Room 2   BUSY
Room 3   BUSY
Room 4   FREE
Room 5   BUSY
...

При большом количестве данных постоянно искать небольшое интересующее
нас подмножество среди всех данных может быть дорого.

## Идея

Помимо основной информации о номерах иметь отдельную структуру,
представляющую availability (доступность).

Концептуально:

Rooms
→ все номера

AvailableRooms
→ только доступные номера

или аналогичное представление занятых номеров.

Тогда запрос:

"Найди свободные номера"

работает уже не со всем набором данных, а с подготовленным
подмножеством.

**ВОПРОС** а как подготовить это подмножество?
# 3. Более общий паттерн: Materialized Subset

Идею с AvailableRooms можно рассматривать шире.

Если система очень часто выполняет запрос:

"Найди объекты, удовлетворяющие условию X"

вместо постоянного вычисления X по всему набору данных можно
поддерживать отдельное заранее подготовленное представление.

Например:

All Items
   ↓
┌──────────────┐
│ item 1       │
│ item 2       │
│ item 3       │
│ ...          │
│ item 1 000M  │
└──────────────┘

и отдельно:

Available Items
   ↓
┌──────────────┐
│ item 17      │
│ item 193     │
│ item 840     │
└──────────────┘

Мы платим дополнительной:

- storage (памятью/хранилищем);
- write complexity (сложностью записи);
- необходимостью поддерживать представление актуальным;

но ускоряем часто выполняемые read queries (запросы чтения).

Это общая идея:

> Перенести часть вычислений с read path (пути чтения)
> на write/update path (путь записи/обновления).

# 4. Race Condition при бронировании

Теперь возникает более серьёзная проблема.

Представим, что остался один доступный номер:

available = 1

Одновременно приходят два пользователя:

User A ──┐
         ├──→ пытаются забронировать номер
User B ──┘

Оба могут увидеть:

available = 1

и решить, что номер можно забронировать.

Получаем overbooking (двойное бронирование).

Это race condition (гонка).

---

# 5. Atomic Counter (атомарный счётчик доступного ресурса)

В примере из курса предлагается хранить количество доступных номеров:

count: int

и установить constraint (ограничение):

count >= 0

Например:

room_type | count
----------|------
Standard  | 3
Deluxe    | 1
Suite     | 0

При бронировании:

count = count - 1

Причём изменение должно происходить атомарно на стороне БД.

Концептуально:

UPDATE availability
SET count = count - 1
WHERE room_type = ?
  AND count > 0;
```

Если обновилась одна строка:

```text
booking allowed
```

Если ни одной:

```text
no availability
```

Таким образом проверка:

```text
count > 0
```

и изменение:

```text
count = count - 1
```

происходят как одна атомарная операция.

---

# 6. Почему это защищает от Race Condition

Представим:

count = 1

Одновременно приходят:

User A
User B

Оба пытаются выполнить:

count = count - 1
WHERE count > 0

Один запрос успешно изменяет:

1 → 0

После этого условие второго:

count > 0

уже не выполняется.

В результате:

User A → booking successful
User B → booking rejected

И мы не получаем:

count = -1

или две продажи последнего доступного ресурса.

---

# 7. Более общий паттерн: Conditional Atomic Update

Этот приём относится не только к Booking.

Общая задача:

> Есть ограниченный ресурс, и несколько клиентов одновременно
> пытаются его получить.

Вместо схемы:

READ
 ↓
проверить значение в приложении
 ↓
WRITE

используем:

ATOMIC CONDITIONAL UPDATE
(атомарное условное изменение)

То есть проверка условия и изменение состояния происходят
одной операцией в системе хранения.

Например:

UPDATE resource
SET available = available - 1
WHERE id = ?
  AND available > 0;

Этот подход применим для:

- бронирования номеров;
- покупки ограниченного количества товара;
- резервирования билетов;
- использования квот;
- выдачи ограниченного количества ресурсов.

Главная идея:

> Не делаем отдельно "прочитал → проверил → изменил",
> если между этими операциями другой конкурентный запрос может
> изменить состояние.

По возможности выражаем условие непосредственно внутри
атомарной операции изменения.

---

# 8. Locks vs Atomic Conditional Update

Альтернативой может быть явная блокировка ресурса.

Например:

lock room
 ↓
check availability
 ↓
create booking
 ↓
update availability
 ↓
unlock room

Но блокировки увеличивают contention (конкуренцию за ресурс)
и могут уменьшать throughput (пропускную способность).

Если бизнес-операцию можно выразить через простой атомарный
conditional update (условный update), такой вариант может быть
значительно проще и дешевле.

Это не означает, что atomic counter всегда заменяет блокировки.

Главный вопрос:

> Можно ли выразить необходимый invariant (инвариант системы)
> одной атомарной операцией?

В нашем примере invariant:

count >= 0

---

# 9. Несколько Payment Providers (платёжных провайдеров)

Платёжный сервис является внешней зависимостью.

Если используется только один provider:

Booking
   ↓
Payment Provider A
   ↓
DOWN

то система может потерять возможность принимать оплаты.

Один из вариантов повышения availability (доступности):

             ┌──→ Payment Provider A
Booking ─────┤
             └──→ Payment Provider B

Если один провайдер недоступен, можно использовать другой.

Это пример redundancy (избыточности) внешней зависимости.

Конкретную механику переключения между платёжными системами
пока не рассматриваем.

# Что важно вынести из кейса

## 1. Разные типы клиентов могут иметь разные API

Client API ≠ Owner API

При необходимости можно разделить и API Gateway.

## 2. Часто используемое подмножество данных можно подготовить заранее

Вместо постоянного поиска:

all rooms → filter available

можно поддерживать:

available rooms

То есть увеличить стоимость записи/обновления ради более дешёвого чтения.

## 3. Ограниченный ресурс удобно представлять счётчиком

Например:

available_rooms = 10

При использовании ресурса:

available_rooms -= 1

## 4. Проверку и изменение желательно делать атомарно

Не:

READ → CHECK → WRITE

а:

ATOMIC:
UPDATE ... WHERE count > 0

Это позволяет бороться с race condition (гонкой).

## 5. Для критичной внешней зависимости можно иметь резерв

Payment Provider A
+
Payment Provider B

чтобы отказ одного провайдера не приводил к полной остановке платежей.
