
Пример: WhatsApp.

Система позволяет пользователям обмениваться сообщениями в личных и групповых чатах.

---

# 1. Functional Requirements (функциональные требования)

Основные возможности:
- поддерживаем групповые чаты и личные сообщения;
- поддерживаем прочитанность сообщений;
- в сообщениях присутствует только текст;
- оповещаем о новых сообщениях online-пользователей (пользователей, которые сейчас находятся в сети);
- поддерживаем cross-device synchronization (синхронизацию между устройствами одного пользователя).
---

# 2. Non-functional Requirements (нефункциональные требования)

- DAU (Daily Active Users — активных пользователей в день): **50 000 000**;
- Availability (доступность): **99.95%**;
- сообщения храним всегда;
- аудитория — страны СНГ;
- сезонности нет.

## Лимиты

- максимальное количество пользователей в чате: **500**;
- максимальное количество символов в сообщении: **2000**.
## Активность

В среднем один пользователь:

- пишет **20 сообщений в день**;
- читает сообщения **100 раз в день**.
## Тайминги

- создание сообщения: **1–2 секунды**;
- получение сообщений: **2–3 секунды**;
- сообщение может доходить до получателя с задержкой **1–3 секунды**.
# 3. Data Model Draft (черновая модель данных)

Для оценки нагрузки сначала прикинем структуру основной сущности.

## Message

```text
message
-------
id
chat_id
user_id
created_at
content
```

В лекции для дальнейших расчётов принимается:

```text
average message size ≈ 4 KB
```

Это оценка размера одного сообщения.

# 4. Capacity Estimation (оценка нагрузки)

## Write RPS

50 млн пользователей отправляют в среднем 20 сообщений в день:

```text
RPS(write/message) = 50 000 000 × 20 / 86 400 ≈ 11 574 RPS
```

То есть система в среднем получает около:

```text
~11.6K новых сообщений / секунду
```

---

## Read RPS

Каждый пользователь в среднем читает сообщения 100 раз в день:

```text
RPS(read/message)
= 50 000 000 × 100 / 86 400 ≈ 57 870 RPS
```

Получаем примерно:

```text
~57.9K read requests / секунду
```

Соотношение:

```text
read : write ≈ 5 : 1
```

То есть система read-heavy (нагрузка смещена в сторону чтения), но перекос не такой большой, как в Social Feed.

# 5. Network Traffic (сетевой трафик)

## Write traffic

Размер одного сообщения принимаем за `4 KB`:

```text
11 574 × 4 KB ≈ 46 MB/s
```

Получаем:

```text
write traffic ≈ 46 MB/s
```

---

## Read traffic

На скриншоте лекции предполагается, что один запрос чтения возвращает примерно **20 сообщений**.

Тогда:

```text
57 870 × 20 × 4 KB ≈ 4.6 GB/s
```

В лекции значение округлено примерно до:

```text
read traffic ≈ 4 GB/s
```

### Важное наблюдение

По RPS:

```text
read / write ≈ 5x
```

Но по объёму передаваемых данных разница значительно больше, потому что:

```text
write request → 1 message

read request → ~20 messages
```

Поэтому при capacity planning (расчёте ресурсов) недостаточно смотреть только на RPS.

Нужно отдельно считать:

- RPS;
- размер request/response;
- network throughput (пропускную способность сети).

# 6. Workload Classification (характер нагрузки)

## Read-heavy (много чтений)

```text
write ≈ 11.6K RPS
read  ≈ 57.9K RPS
```

Чтений примерно в 5 раз больше.

При этом read traffic (трафик чтения) значительно выше write traffic (трафика записи).

---

## Connection-heavy (много долгоживущих соединений)

Для доставки событий online-пользователям требуется поддерживать большое количество постоянных соединений.

Поэтому для Messenger важен не только RPS, но и:

```text
concurrent connections
```

— количество одновременно подключённых клиентов.

---

## Latency-sensitive (чувствительность к задержкам)

Доставка сообщений должна происходить достаточно быстро.

По требованиям:

```text
message delivery ≈ 1–3 sec
```

---

## Почему не разделяем Read и Write?

В Social Feed мы рассматривали разделение чтения и записи, потому что:

- система сильно перекошена в сторону чтения;
- получение ленты является сложной операцией;
- для чтения может использоваться precomputation (предварительное формирование ленты).

В Messenger перекос:

```text
~5 : 1
```

и получение сообщений значительно проще, т.е. нам не нужно делать много группировок, делать ранжирование. Здесь мы просто фильтруем сообщения по автору/чату и всё

Поэтому в рассматриваемой архитектуре автор не разделяет Message Service на отдельные:

```text
Write Service
Read Service
```

Один Message Service обслуживает обе операции.

###  8.2 Chat Service

- получение списка чатов;
- управление информацией о чатах.

### 8.3 Message Service

Отвечает за сообщения:

- создание сообщения;
- получение истории сообщений;
- изменение состояния прочитанности.

Отдельная интересная проблема:

> Как определить, какие сообщения прочитал каждый конкретный участник чата?

Нельзя просто добавить:

```text
message.is_read
```

потому что состояние прочитанности зависит от пользователя + мы должны учитывать синхронизацию между устройствами.

Например:

```text
Chat #123

Message 100
Message 101
Message 102
Message 103
Message 104
```

Alice могла прочитать до:

```text
Message 104
```

а Bob только до:

```text
Message 101
```

Поэтому на лекции используется отдельная структура:

```text
lastseen
--------
chat_id
user_id
message_id
```
#### LastSeen

`LastSeen` хранит последнее прочитанное пользователем сообщение в конкретном чате.

Например:

```text
chat_id | user_id | message_id
--------|---------|-----------
123     | Alice   | 104
123     | Bob     | 101
123     | Charlie | 98
```

Получается:

```text
(chat_id, user_id)
        ↓
last read message_id
```

Если для Bob:

```text
message_id = 101
```

то мы знаем, что пользователь дошёл в этом чате до сообщения `101`.

Таким образом, нам не требуется хранить отдельный `is_read` для каждой комбинации:

```text
message × user
```

Мы храним одну позицию пользователя внутри чата.

Это особенно важно для групповых чатов, где может быть до:

```text
500 участников
```

Возникает ещё одна задача: **как эффективно определить, прочитал ли пользователь последнее сообщение в чате?**

У нас уже есть две таблицы:

- `message` — хранит все сообщения;
    
- `lastseen` — хранит последнее прочитанное сообщение для каждого пользователя в каждом чате.

Чтобы определить, прочитал ли пользователь последнее сообщение, необходимо:

1. Найти последнее сообщение в конкретном чате в таблице `message`.
    
2. Получить `message_id` последнего прочитанного сообщения из `lastseen`.
    
3. Сравнить позиции этих сообщений.
    

Например:

```text
Последнее сообщение в чате: 105
Последнее прочитанное Bob: 101

Bob не прочитал последние сообщения.
```

**Проблема — размер таблицы** `**message**`**.**

Мы уже рассчитали нагрузку на запись:

```text
Write RPS = 11 574

Messages per year:
11 574 × 86 400 × 365
≈ 365 миллиардов сообщений
```
Это огромное количество записей. Если для каждого запроса искать последнее сообщение среди всех сообщений конкретного чата, такой запрос может оказаться дорогим. 

Первое возможное решение — создать индекс, например по `(chat_id, created_at)`. Тогда БД сможет эффективно находить последнее сообщение без полного сканирования таблицы.

Но есть и другой интересный подход - создать еще одну таблицу LastMessage, где будем хранить данные о последнем сообщении в чате.

#### LastMessage — предварительно подготовленные данные

Можно завести отдельную таблицу `last_message`:

```text
last_message
------------
chat_id
message_id
```

Для каждого чата хранится только одна запись — идентификатор последнего сообщения.

Например:

|chat_id|message_id|
|---|---|
|123|105|
|456|870|
|789|42|
При создании нового сообщения мы обновляем соответствующую запись в `last_message`.

Теперь для проверки прочитанности достаточно:

1. Получить `message_id` из `last_message`.
    
2. Получить последнее прочитанное сообщение пользователя из `lastseen`.
    
3. Сравнить их позиции.
    

Таким образом, вместо поиска последнего сообщения в большой таблице мы обращаемся к небольшой структуре, в которой уже хранится нужный результат.

На `chat_id` можно создать индекс. В частности, можно рассмотреть hash index (хэш-индекс), поскольку поиск выполняется по точному значению `chat_id`. При этом обычный B-tree index (B-дерево) тоже подходит для такого запроса.

**Главная идея:**

Мы заранее сохраняем результат часто выполняемого запроса, чтобы ускорить последующие чтения.

Это особенно интересно для нашей системы, поскольку она read-heavy (с преобладанием операций чтения).

**Trade-off (компромисс):**

- Чтение становится дешевле.
    
- При записи сообщения необходимо дополнительно обновлять `last_message`.
    
- Нужно обеспечивать согласованность `message` и `last_message`.
    

То есть мы сознательно увеличиваем стоимость записи ради ускорения чтения.

### 8.4 Notification Service

Отвечает за доставку событий online-пользователям.

Данные для уведомлений будут ходить через Кафку из Message service в Notification Service. Если нам окей, что какие-то данные могут потеряться и пользователь не получит уведомление, то можно писать в Кафку без Outbox(или CDC). Но если всё-таки нам точно нужно гарантировать, что все сообщение дойдут, тогда применяем CDC или Outbox

Notification service доставляет уведомления пользователю с помощью WS соединений. Также Notification service должен ходить в Chat service, т.к. нам нужно понимать, кто находится в чате вместе с пользователем, написавшим сообщение. Между Notification и Chat можно поставить какой-нибудь кэш, который мы будем как-то обновлять

Также стоит подумать о кол-ве хостов для Notification service, т.к. мы ограничены кол-вом открытых соединений в один момент. Можно прикинуть, сколько у нас будет соединений. Скажем, что кол-во открытых соединений это 10% от DAU, тогда 
```
connections = 50 000 000 * 0.1 = 5 000 000 
```
Достаточно много. Стоить уточнить у интервьюэра, а сколько соединений держит наш хост

Notification service не имеет storage, т.к. это не нужно, мы просто в нем управляем connection'ами пользователей. Мы храним их в памяти, скорее всего в мапе. Поэтому здесь может быть проблема, а что если у нас откажет Notification service. Мы можем иметь сразу запасной сервис и переподключать соединения, если первый вышел из строя. Тогда нам нужен балансер перед ними.

#### Проблема распределения WebSocket-соединений

Ранее мы рассчитали количество одновременно открытых соединений:

```text
DAU = 50 000 000
Online users = 10%

Connections:
50 000 000 × 0.1 = 5 000 000
```

Один экземпляр `Notification Service` может не справиться с таким количеством соединений.

Поэтому мы запускаем несколько экземпляров сервиса и распределяем между ними пользователей.

Например:

```text
Notification Service A
    └── WebSocket: Вова

Notification Service B
    └── WebSocket: Дима

Notification Service C
    └── WebSocket: Алёна
```

При этом Вова, Дима и Алёна находятся в одном чате.

**Проблема:**

Вова отправляет сообщение.

Как уведомить Диму и Алёну, если их WebSocket-соединения находятся на других экземплярах `Notification Service`?

#### Решение — каждый экземпляр получает события из Kafka

Можно организовать **broadcast/fan-out**(широковещательное распространение событий) между экземплярами `Notification Service`.

Каждый экземпляр получает события о новых сообщениях из Kafka.

При получении события экземпляр:

1. Определяет `chat_id`, в котором появилось сообщение.
    
2. Обращается к `Chat Service`, чтобы получить участников чата.
    
3. Проверяет, какие из этих пользователей имеют активные WebSocket-соединения именно с ним.
    
4. Отправляет уведомления только этим пользователям.
    

Например:

```text
Вова отправляет сообщение
          |
          v
    Message Service
          |
          v
        Kafka
          |
          +-----------------------+
          |           |           |
          v           v           v
    Notification  Notification  Notification
      Service A     Service B     Service C
          |           |           |
          v           v           v
       Проверка    Проверка    Проверка
       локальных   локальных   локальных
       соединений  соединений  соединений
          |           |           |
          -           v           v
                     Дима        Алёна
```

Каждый экземпляр хранит информацию о собственных активных соединениях в оперативной памяти, например:

```python
connections: dict[user_id, WebSocket]
```

Поэтому он может быстро определить, подключён ли конкретный пользователь именно к нему.

#### Недостаток такого подхода

Каждый экземпляр получает событие, даже если ни один участник чата к нему не подключён.

Например:

```text
Notification Service D
    └── нет участников чата

Но событие всё равно получено.
```

Это приводит к дополнительным затратам:

- Network traffic (сетевой трафик) — одно событие доставляется нескольким экземплярам.
    
- CPU (процессорные ресурсы) — каждый экземпляр обрабатывает событие.
    
- Chat Service load (нагрузка на сервис чатов) — экземпляры могут выполнять одинаковые запросы за списком участников.
    
- Лишняя работа — часть экземпляров не отправит ни одного уведомления.
    

В качестве частичной оптимизации можно использовать cache (кэш) участников чата, чтобы не обращаться к `Chat Service` при каждом событии.

**Главная идея:**

Когда WebSocket-соединения распределены между несколькими экземплярами сервиса, возникает задача маршрутизации событий к нужным соединениям.

**Broadcast(fan-out)** — простой вариант решения, но он увеличивает объём лишней работы.

В дальнейшем можно рассмотреть более эффективную маршрутизацию событий.

##### Один важный нюанс с Kafka

Здесь стоит отдельно отметить то, чего пока нет в заметках: обычная consumer group (группа потребителей) Kafka не обеспечивает broadcast между экземплярами.

Если все три `Notification Service` используют одну consumer group, каждое сообщение из конкретной партиции будет обработано только одним участником группы.

Для описанного подхода каждый экземпляр должен получать все нужные события, например через отдельную consumer group на экземпляр. Это работает, но количество таких групп и нагрузка растут вместе с числом экземпляров. Либо сами Notification сервисы должны общаться между собой. Т.е. какой-то один сервис получил сообщение из Кафки и дальше он сам рассказал остальным сервисам

# 9. Важные выводы из кейса

### RPS недостаточно

Нужно учитывать не только:

```text
requests / second
```

но и объём данных одного запроса.

В нашем случае:

```text
write → ~1 message
read  → ~20 messages
```

Поэтому сетевой трафик чтения значительно больше.

---

### Не нужно автоматически разделять Read и Write

Сначала анализируем характер нагрузки.

Для Social Feed такое разделение может быть оправдано.

Для этого Messenger автор оставляет единый Message Service.

---

### Read status (статус прочтения) можно хранить как position (позицию)

Вместо:

```text
message × user → read/unread
```

можно хранить:

```text
chat + user → last_seen_message
```

Это значительно компактнее для последовательной истории сообщений.
