
Примеры: лента ВКонтакте, Instagram, Facebook, лента новостей

**Feed (лента)** — поток контента, который система формирует и показывает пользователю на основе публикаций друзей или подписок.

---

# 1. Functional Requirements (функциональные требования)

- публикация постов с текстом и изображениями;
- добавление и удаление друзей;
- получение ленты публикаций.

---

# 2. Non-functional Requirements (нефункциональные требования)

В примере из курса:

- DAU (Daily Active Users — активные пользователи за день) — `50 000 000`;
- availability (доступность) — `99.99%`;
- посты храним постоянно;
- средний размер загружаемого медиа 1Mb
- пользователь в среднем создаёт `1 пост в 5 дней`;
- пользователь в среднем просматривает ленту `5 раз в день`;
- создание поста — `1–2 секунды`.
- размер ленты 20 постов

Также при проектировании необходимо уточнить:

- максимальное количество друзей;
- максимальное количество символов в посте;
- максимальное количество изображений в посте;
- допустимую latency (задержку) получения ленты.

# 4.Capacity Estimation (оценка нагрузки)

## 4.1 RPS

### Write RPS (запросы на запись)
В среднем пользователь создаёт один пост раз в 5 дней:
```
RPS(write/post) = 50 000 000 / 5 / 86 400 ≈ 115 RPS
```

### Read RPS (запросы на чтение)
```
RPS(read/post) = 50 000 000 × 5 / 86 400 ≈ 2 893 RPS
```

## 4.2 Network Traffic (сетевой трафик)

### Write / Media

При создании поста загружается примерно `1 MB`(см. нефункциональные требования) media:
```
115(write RPS) × 1 MB≈ 115 MB/s
```
### Write / Metadata
Размер metadata одного поста — примерно `2 KB`(такое допущение было принято в курсе):
```
115(write RPS) × 2 KB ≈ 230 KB/s
```

### Read / Media

В примере предполагается, что при получении ленты пользователь получает примерно `20` постов:
```
2 893(read RPS) × 20 × 1 MB ≈ 57 GB/s
```

### Read / Metadata

```
2 893(read RPS) × 20 × 2 KB ≈ 115 MB/s
```

## 4.3 Storage Capacity (объём дискового хранилища)

У нас:

```
50 000 000 DAU
1 пост в 5 дней

Posts/day = 50 000 000 / 5 = 10 000 000 постов/день
```
#### Metadata

Один пост ≈ `2 KB`:

```
10 000 000 × 2 KB = 20 000 000 KB ≈ 20 GB/day
```

За год:

```
20 GB × 365 ≈ 7 300 GB ≈ 7.3 TB/year
```

#### Media

В лекции принимаем `1 MB` media на пост:

```
10 000 000 × 1 MB = 10 000 000 MB ≈ 10 TB/day
```

За год:

```
10 TB × 365 ≈ 3 650 TB ≈ 3.65 PB/year
```

Итого raw storage (сырой объём данных):

```
Metadata ≈ 7.3 TB/year
Media    ≈ 3.65 PB/year

Total    ≈ 3.66 PB/year
```

Это **без replication (репликации)**.

Если, например, `replication factor = 3`:

```
3.66 PB × 3 ≈ 10.98 PB ≈ 11 PB
```

То есть физически потребуется порядка **11 PB storage в год**.

Но здесь есть важная оговорка: мы пока считаем очень грубо и предполагаем **ровно 1 MB media на каждый пост**. Если в посте может быть несколько изображений, расчёт нужно делать через `average media size per post (средний объём медиа на пост)`.

Возможно можно применить сжатие к файлам, но это замедлит выдачу т.к. нам нужно будет разжимать файлы

## 4.4 Считаем количество дисков по capacity (ёмкости)

### 4.4.1 Кол-во HDD

Допустим, для грубой оценки у нас:

```
1 HDD = 20 TB
```
### 4.4.1 Кол-во SSD

Для учебного расчёта нам нужно сделать assumption (допущение), потому что SSD бывают очень разными.

Возьмём условный SSD:

```
Capacity:   8 TB
Throughput: 1 GB/s
IOPS:       100 000
```

У нас с `replication factor = 3`:

```
≈ 11 PB/year ≈ 11 000 TB/year
```

По capacity (ёмкости):

```
11 000 TB / 8 TB ≈ 1 375 SSD
```

Получается забавная ситуация:

```
20 TB HDD → ~550 дисков
8 TB SSD  → ~1 375 дисков
```

SSD быстрее, но в нашем примере он меньше по объёму.

Если взять SSD на `16 TB`:

```
11 000 / 16 ≈ 688 SSD
```

Поэтому для огромного object storage (объектного хранилища) HDD может быть экономически выгоднее, если основной bottleneck (узкое место) — **capacity**, а не latency/IOPS.

Но возможно мы можем разделить данные на холодные/теплые/горячие. Тогда какие-то данные будут храниться на SSD,а какие-то на HDD

## 4.5 Считаем Throughput

### 4.5.1 Write Throughput

Из наших предыдущих расчётов:

```
Media write traffic ≈ 115 MB/s
```

С `replication factor = 3` физически кластер должен записывать примерно:

```
115 MB/s × 3 ≈ 345 MB/s
```

Допустим для учебной оценки:

```
1 HDD sequential write throughput ≈ 200 MB/s
```

Тогда чисто математически:

```
345 / 200 ≈ 1.7
```

То есть всего **~2 HDD** уже могли бы обеспечить требуемый sequential write throughput (пропускную способность последовательной записи).

А по capacity нам нужно **550 дисков**.

Следовательно:

```
Capacity HDD requirement:   550 HDD
Capacity SSD requirement:
Write throughput:        ~2 HDD
```

В этом упрощённом примере bottleneck (ограничивающим фактором) является **capacity**, а не write throughput.

### 4.5.2 Read Throughput
Мы выше получили очень большой media traffic:

```
≈ 57 GB/s
```

Если представить, что всё это читается непосредственно с HDD:

```
57 GB/s = 57 000 MB/s
```

При:

```
~200 MB/s per HDD
```

получаем:

```
57 000 / 200 ≈ 285 HDD
```

То есть по sequential read throughput:

```
≈ 285 HDD
```

А у нас из-за capacity уже:

```
≈ 550 HDD
```

Получается, даже здесь наши 550 дисков теоретически дают достаточный aggregate throughput (суммарную пропускную способность):

```
550 × 200 MB/s ≈ 110 GB/s
```

## 4.6 Считаем IOPS

Возьмем, что для одного HDD IOPS=150 

Тогда:
```
550(кол-во HDD) * 150(IOPS per disc) = 82 500 IOPS available
```

**Required IOPS мы пока не можем точно определить только из `57 GB/s`**.

Нам нужен ещё один параметр:

> **Каков средний размер одной физической I/O operation (операции ввода-вывода)?**

Например, рассмотрим media. У нас assumption:

```
Average image = 1 MB
```

Если условно считать, что чтение одного изображения — одна I/O operation:

```
Read traffic ≈ 57 GB/s

57 GB/s / 1 MB ≈ 57 000 operations/s
```

То есть:

```
Required read IOPS ≈ 57 000
```

А 550 HDD дают:

```
Available IOPS ≈ 82 500
```

Получается:

```
Required:  ~57 000 IOPS
Available: ~82 500 IOPS

82 500 > 57 000
```

В этой **сильно упрощённой модели** хватает.

Но теперь представь, что средняя операция не `1 MB`, а `4 KB`.

При тех же `57 GB/s`:

```
57 GB/s / 4 KB ≈ 14 250 000 IOPS
```

И наши:

```
82 500 HDD IOPS
```

уже вообще не справляются.

Вот почему **размер I/O operation критически важен**.

Часто в подобных сервисах перед хранилищем стоит CDN, поэтому реальное IOPS еще меньше

# 5. Workload Classification (характер нагрузки)

Из предыдущих расчётов уже можно сделать вывод о характере системы. У нас большой перекос в сторону чтения(Read-heavy) - почти 3000 RPS против 115 RPS.  Из-за этого у нас также большая нагрузка на сеть и диски из-за медиа. Поэтому доставка media становится отдельной важной частью архитектуры.

Поэтому систему имеет смысл в первую очередь оптимизировать под быстрое получение ленты. Поэтому стоит подумать на счет пре-расчетов ленты, т.е. лента должна быть сформирована перед тем, как пользователь захочет ее получить, а не вовремя захода на страницу ленты. Также будет проблема селебретис, это нужно учесть. Т.к. появление их постов может задевать миллионы пользователей

# 7. High-Level Design (верхнеуровневая архитектура)


![[систем_дизайн_лента_вк.drawio.svg]]



В разборе система разделялась на несколько компонентов:

- API Gateway;
- Post Service(отвечает за посты пользователей, здесь создаем посты);
- Media Service(отвечает за медиа пользователей, которое прикрепляется к постам);
- Relation Service(отношения между людьми)
- Timeline service(сервис чтения / формирования ленты. Здесь юзер читает свой пост);
- хранилище постов;
- хранилище подготовленных лент;
- object storage (объектное хранилище) для media(внутри хранилища можно сделать два бакета temp и main. Далее по тексту будет объяснение);
- CDN (Content Delivery Network — сеть доставки контента).

Операции записи и чтения постов были разделены.

Причина — система сильно перекошена в сторону чтения, а получение ленты требует другой логики и имеет другой профиль нагрузки, чем создание поста.

# 8. Component Deep Dive (заметки по компонентам)

## 8.1 Precomputed Feed (предварительно сформированная лента)

Вместо полного формирования ленты во время каждого запроса её можно подготовить заранее. Для переливания данных из Post storage в Timeline service используем кафку. При создании поста нам нужно записать данные из в Post storage, и в кафку. Используем Outbox-паттерн(через таблицу post_outbox) для этого

```
Создание поста
      ↓
обновление пользовательских лент
      ↓
Feed Storage
      ↓
быстрое получение ленты
```

Для сервиса чтения можно использовать Key-Value Database (БД типа «ключ-значение»), поскольку мы храним заранее подготовленные данные для конкретного пользователя.

Концептуально:

```
user_id → prepared feed
```
Также стоит отметить, что у нас у каждого пользователя две ленты.
	1. user_timeline. Здесь хранятся посты самого пользователя
	2. home_timeline. Здесь хранятся посты пользователя на основе его отношений. Т.е. здесь будут посты его друзей

Ленту необходимо перестраивать, когда:
- создаётся новый пост;
- пользователь добавляет друга;
- пользователь удаляет друга.

Как происходит перестраивание ленты. 
	1. Я создаю пост. Мне нужно перестроить свою ленту и ленту моих друзей. Флоу может быть таким: пост попадает в Post storage, оттуда в кафку, оттуда в Timeline service. В timeline service я перестраиваю свою ленту, иду в relation service, узнаю информацию о своих друзьях/подписчиках и перестраиваю их ленты
	2. Если создается/удаляется друг. Тогда relation service кладет информацию в кафку, ее читает Timeline сервис и перестраивает ленты

Таким образом мы делаем write path (путь записи) тяжелее ради более дешёвого read path (пути чтения). 

Но тут есть еще один момент. Если пользователь пролистал всю ленту, то ему нужно сходить и получить еще посты. Тогда Timeline service может напрямую сходить в Post service

## 8.2 Celebrity Problem (проблема знаменитостей)

Возникает проблема пользователей с огромным количеством подписчиков.

```
Celebrity
    ↓
создаёт пост
    ↓
миллионы подписчиков
    ↓
миллионы обновлений feed
```

Один пост может породить огромное количество операций обновления лент.

Это крайний случай fan-out (распространения одного события на большое количество получателей), который необходимо отдельно учитывать.

Как можно решить проблему, когда очень известная личность(много друзей) делает пост. Для самой этой известной личности мы меняем только его ленту(user_timeline). Ленты его друзей/подписчиков не трогаем, т.к. нам нужно будет сделать много работы. А вот когда уже его друг(не селебрити) зайдет посмотреть в ленту, то мы можем смотреть, на каких селебрити он подписан и подмерживать новые посты. Информацию о том, на каких селебрити подписан пользователь можно кэшировать

## 8.3 Разделение Post и Media

В разборе загрузка media и создание самого поста разделялись.

```
Post metadata → Database

Media → Object Storage
```

Media Service сохраняет изображения в S3-like storage (S3-подобное объектное хранилище).

В качестве примера такого хранилища в курсе упоминался Ceph.

Так большие бинарные объекты не приходится хранить непосредственно вместе с metadata поста.

## 8.4 Temporary Media (временное хранение медиа)

Есть важная проблема:

```
пользователь загрузил изображение
              ↓
Media Service сохранил файл
              ↓
пользователь НЕ создал пост
```

Получаем orphan media (медиа-файл без связанного поста).

В разборе предлагалось использовать два bucket (контейнера объектного хранилища):

```
temp
main
```

При загрузке:

```
Upload
   ↓
temp
```

У media должна храниться метка времени создания.

Старые файлы из `temp`, которые так и не были использованы, можно периодически удалять.

При этом нельзя удалять их слишком быстро: информация о созданном посте могла ещё не успеть дойти до Media Service. 
## 8.5 CDC для Post Storage -> Media storage

Media Service должен каким-то образом узнать, что Post Service успешно создал пост с определённым media.

В разборе использовался CDC (Change Data Capture — получение изменений из БД).

```
Post Service
     ↓
Post Database
     ↓
    CDC
     ↓
Media Service
     ↓
temp → main
```

Таким образом изменения в Post Database становятся источником информации для Media Service. При этом пользователь может начать читать пост, у которого медиа еще не успела переехать из temp в main. При запросах нужно запрашивать данные из двух бакетов.

## 8.6 CDN для Media

Пользователь получает изображения через CDN (Content Delivery Network — сеть доставки контента).

```
Object Storage
       ↓
      CDN
       ↓
     User
```

CDN позволяет:

- отдавать контент с географически близких к пользователю узлов;
- уменьшать latency (задержку);
- снизить нагрузку на основное object storage;
- уменьшить объём трафика, который должен непосредственно обслуживать backend.

Также можно рассмотреть такой случай, когда пользователь может получать медиа напрямую через CDN(или Media storage), а не через Gateway -> Media service. Если трафик большой, то такой подход будет предпочтительней

## 8.7 Timeline storage

В timiline storage мы храним данные в виде ключ-значение(возможно in-memory), т.к. здесь хранятся те посты, которые мы должны отобразить пользователям. Т.е. ключ - это user_id, а значение - это массив объектов, которые содержат метаинформацию о посте, которая пришла к нам из Post storage. Важно понимать, что надо прикинуть, а сколько данных мы будем хранить. Возможно in-memory вариант нам не подойдет, т.к. это слишком дорого

Прикинем кол-во данных:

50000000(DAU) * 20(кол-во постов в ленте) * 4 KB = 8 TB

# 9. Важные идеи из кейса

## 9.1 Read-heavy → Precomputation

Если чтений значительно больше записей, можно сделать запись дороже, чтобы заранее подготовить данные для последующего быстрого чтения.

---

## 9.2 Fan-out

Нужно смотреть не только на количество входящих запросов.

Одна операция пользователя может породить огромное количество внутренних операций системы.

```
1 CreatePost
      ↓
N feed updates
```

---

## 9.3 Metadata и Media можно хранить отдельно

```
metadata → Database
media    → Object Storage
```

Особенно важно для систем с большими файлами.

---

## 9.4 Temp → Main

Если ресурс создаётся раньше основной бизнес-сущности:

```
upload
  ↓
temp storage
  ↓
business operation
  ↓
main storage
```

Неиспользованные временные данные впоследствии удаляются.

Этот приём применим не только к социальной сети.
