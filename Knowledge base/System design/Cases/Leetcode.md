 LeetCode

Пример сервиса для проверки решений задач по программированию на Go.

Главная особенность — выполнение пользовательского кода. Поэтому важно учитывать не только RPS, но и вычислительную стоимость каждой проверки.

# 1. Functional Requirements (функциональные требования)

- Проверка решений задач на Go.
- Тестирование кода без сохранения решения.
- Отправка решения на проверку с последующим сохранением.

# 2. Non-functional Requirements (нефункциональные требования)

- Количество задач: **1 000**.
- DAU (активных пользователей в день): **10 000 000**.
- Availability (доступность): **99,95%**.
- Средняя активность: **4 проверки кода на пользователя в день**.
- Latency (задержка) проверки: **не более 2 секунд**.
- Ограничение частоты запуска: **один запуск кода в 5 секунд на пользователя**.
- Максимальный размер кода: **2 KB**.
- Необходимо обеспечить безопасное выполнение пользовательского кода.
- Выраженной сезонности в рамках задачи нет.

# 3. Data Model (модель данных)

## 3.1 Task Service — задачи

На схеме задачи хранятся в **MongoDB (документной БД)**.

```text
Task:
- task_id
- title
- description
- test_cases: [test_case1, test_case2, ...]
```

Количество тест-кейсов различается: **20, 50, 90 и т. д.** Поэтому документная модель удобна: тесты можно хранить вместе с задачей. Само по себе переменное число тестов не означает, что обязательно нужна MongoDB, — это выбор из лекции.

## 3.2 Check Service — кэш

На схеме показана **in-memory key-value DB (ключ-значение в оперативной памяти)**, например Redis или Tarantool.

```text
task_id -> [test_case1, test_case2, ...]

(user_id, task_id) -> hash(code)
```

Первая структура — кэш тест-кейсов. 
Вторая — идея обнаружения повторной отправки одинакового кода одним пользователем для одной задачи.

Для полноценного повторного использования результата проверки одного хэша недостаточно: нужно сохранить сам результат или ссылку на него. Также при изменении тестов прежний результат может стать неактуальным.

## 3.3 Solution Service — решения

На схеме для решений предусмотрены два хранилища:

- **PostgreSQL** — metadata (метаданные решения).
- **S3-like storage (объектное хранилище)** — исходный код решения.

```text
solution:
- solution_id
- user_id
- task_id
- status (approved / failed)
- created_at
- solution_key / url
```

`solution_key / url` связывает запись в PostgreSQL с сохранённым кодом в объектном хранилище.

# 4. Capacity Estimation (расчёт нагрузки)

## 4.1 RPS

**Проверка кода:**

```text
RPS(execute) = 10 000 000 × 4 / 86 400 ≈ 463 RPS
```

**Получение задачи:** если предположить те же 4 чтения задачи на пользователя в день:

```text
RPS(read task) = 10 000 000 × 4 / 86 400 ≈ 463 RPS
```

Это средняя нагрузка, без пикового коэффициента.

## 4.2 Network Traffic (сетевой трафик)

**Ingress (входящий трафик) проверки:** используем максимальный размер кода 2 KB как консервативную оценку полезной нагрузки.

```text
463 × 2 KB ≈ 0,93 MB/s
```

**Ingress (входящий трафик) проверки:** предположим, что ответ занимает 2 KB.

```text
463 × 2 KB ≈ 0,93 MB/s
```

**Egress получения задач:** предположим, что условие задачи занимает 10 KB.

```text
463 × 10 KB ≈ 4,63 MB/s
```

**Итого для рассмотренных клиентских запросов:**

```text
Ingress ≈ 0,93 MB/s
Egress ≈ 0,93 + 4,63 ≈ 5,56 MB/s ≈ 44,5 Mbit/s
```

Не учтены внутренние запросы, передача тест-кейсов, накладные расходы протоколов и пиковая нагрузка. Размер ответа 2 KB и размер задачи 10 KB — наши допущения, а не требования лекции.

## 4.3 CPU и RAM для Check Engine

В лекции используются следующие предположения:

- одна одновременно выполняемая проверка занимает **1 CPU core (ядро процессора)**;
- одна проверка потребляет **32 MB RAM (оперативной памяти)**;
- один хост имеет **16 CPU cores и 512 GB RAM**;
- для приблизительного расчёта берём множитель 3 к RPS.

```text
Concurrent executions ≈ 462 × 3 = 1 386

CPU cores ≈ 1 386
RAM ≈ 1 386 × 32 MB ≈ 44 352 MB ≈ 44,4 GB

Hosts by CPU = ceil(1 386 / 16) = 87
Hosts by RAM = ceil(44400 MB / 512MB) = 86

Required hosts ≈ max(87, 86) = 87
```


**Важное уточнение:** множитель 3 означает примерно 3 секунды одновременного выполнения при потоке 462 запросов/сек. Его нельзя автоматически выводить из ограничения «одна проверка должна завершиться за 2 секунды». Для корректной оценки нужно знать фактическое среднее время занятости ядра, степень параллелизма и желаемую утилизацию. В конспекте это предварительная оценка, без резерва и системных накладных расходов.

# 5. Workload Characteristics (характер нагрузки)

RPS не высокий, но из-за CPU нагрузки есть свои особенности

## CPU-heavy (высокая нагрузка на процессор)

Даже около 463 RPS могут требовать большой пул вычислительных ресурсов, потому что каждый запрос запускает пользовательский код и тест-кейсы.

## Security-sensitive (критичность изоляции)

Пользовательский код недоверенный: он может зависнуть, потреблять слишком много ресурсов или пытаться обратиться к окружению исполнения.

## Infrastructure-heavy (сложная вычислительная инфраструктура)

Для выполнения пользовательского кода нам потребуется большой пул вычислительных хостов.

Основная трудность — не просто выделить эти серверы, а поддерживать всю инфраструктуру:

- Распределять задачи между хостами через Scheduler (планировщик).
    
- Следить за загрузкой CPU и RAM.
    
- Масштабировать количество хостов при увеличении нагрузки.
    
- Обрабатывать отказы хостов и перераспределять незавершённые задачи.
    
- Обеспечивать безопасное выполнение пользовательского кода в изолированных контейнерах.
    

Также нужно учитывать стоимость инфраструктуры: большое количество вычислительных хостов может быть дорогим в обслуживании.

![[систем_дизайн_leetcode.drawio.svg]]

## 7.1 API Gateway и Rate Limiter

**API Gateway (шлюз API)** принимает запросы и направляет их соответствующим сервисам.

На схеме перед основной обработкой расположен **Rate Limiter (ограничитель частоты запросов)**. Его полезно применять как можно раньше, чтобы лишние запросы не доходили до дорогого Check Engine.

В рамках требований пользователь может запускать код **не чаще одного раза в 5 секунд**. Это ограничение частоты запросов, а не максимальная длительность выполнения одного запуска.

## 7.2 Task Service

Хранит условия задач и тест-кейсы в MongoDB, отдаёт задачи пользователю и данные, необходимые для проверки.

## 7.3 Check Service

Принимает запрос на проверку, получает тест-кейсы (из Task Service или кэша), передаёт работу в Check Engine и обрабатывает результат.

### Кэш тест-кейсов

Чтобы при каждой проверке не обращаться к Task Service, можно кэшировать тест-кейсы по `task_id`.

Нужно предусмотреть заполнение кэша при отсутствии записи и поведение при его отказе: на схеме показана возможность обратиться к основному хранилищу задач.

### Повторная отправка одинакового кода

Если пользователь дважды отправил один и тот же код для одной задачи, повторная проверка может зря расходовать CPU.

```text
(user_id, task_id) -> hash(code)
```

По хэшу можно обнаружить повтор. Для возврата готового ответа также потребуется результат прошлой проверки; желательно учитывать версию тест-кейсов. Вычисление хэша намного дешевле повторного запуска Check Engine, но тоже требует небольших ресурсов.

## 7.4 Check Engine

Отвечает за непосредственное выполнение кода и проверку тест-кейсов.

Внутри предусмотрены:

- **Scheduler (планировщик)** — распределяет проверки между хостами;
- **пул хостов** — вычислительные машины, на которых выполняются задачи;
- **daemon (демон)** — процесс на хосте, принимающий задания и запускающий проверки.

### Изоляция пользовательского кода

Из лекции: можно запускать каждую проверку в отдельном Docker-контейнере.

Контейнер помогает ограничивать ресурсы и изолировать процессы, но **сам по себе не гарантирует безопасное выполнение недоверенного кода**. Для реальной системы нужны дополнительные ограничения и защита среды исполнения. Подробную реализацию в рамках этого конспекта не проектируем.

## 7.5 Solution Service

Отвечает за сохранение решений:

- код — в S3-like storage;
- метаданные и статус — в PostgreSQL.

В рассматриваемом потоке после успешной проверки Check Service обращается к Solution Service, чтобы сохранить принятое решение.

**Примечание:** исходные функциональные требования также предусматривают тестирование без сохранения. Поэтому сохранять результат нужно только в сценарии отправки решения, а не после любой успешной проверки.

# 8. Основные сценарии

## 8.1 Получение задачи

```text
User → API Gateway → Task Service → MongoDB
```

## 8.2 Проверка кода

```text
User
  ↓
API Gateway / Rate Limiter
  ↓
Check Service
  ├── тест-кейсы из cache / Task Service
  ↓
Check Engine
  ├── Scheduler
  └── daemon на вычислительном хосте
  ↓
Результат проверки
```

## 8.3 Отправка и сохранение решения

```text
User → API Gateway → Check Service → Check Engine
                                       ↓
                                Проверка успешна
                                       ↓
                                Solution Service
                                  ├── PostgreSQL (метаданные)
                                  └── S3 (код)
```

Это упрощённый сценарий из заметок; детали статусов и неуспешных проверок не определены.

# 9. Надёжность и отказоустойчивость

- Для БД предусматриваем репликацию, как отмечено в лекции.
- При отказе кэша Check Service должен иметь возможность получить тест-кейсы из основного источника, если он доступен.
- При отказе вычислительного хоста важно понимать, что происходит с уже запущенной проверкой. Конкретный механизм повторного запуска в заметках не задан.

# 10. Интересные моменты и Corner Cases (пограничные случаи)

### 10.1 Один и тот же код отправлен дважды

Повторная проверка тратит CPU. Можно использовать хэш кода и кэш результата, но нужно учитывать изменение тест-кейсов.

### 10.2 Кэш тест-кейсов пуст или недоступен

Check Service может получить данные из Task Service. Это увеличит нагрузку на основной источник.

### 10.3 Пользователь слишком часто запускает проверки

Rate Limiter на входе не пропускает лишние запросы к дорогим вычислительным компонентам.

### 10.4 Пользовательский код завис или ведёт себя вредоносно

Необходима изоляция запуска и ограничения ресурсов. Docker — вариант из лекции, но не исчерпывающая гарантия безопасности.

### 10.5 CPU закончились раньше RAM

В рассматриваемом расчёте 16-ядерный хост ограничен числом параллельных проверок, хотя большая часть RAM остаётся свободной.

### 10.6 Check Engine или вычислительный хост отказал во время проверки

Нужно определить, как Scheduler узнаёт об отказе и что делать с незавершённой задачей. В лекционных заметках механизм не раскрыт — оставляем вопрос для дальнейшего разбора.

### 10.7 Сохранение решения после проверки

Тестирование и отправка решения — разные сценарии. Успешная проверка не всегда означает, что решение нужно сохранять.

## Главные выводы

1. **RPS не равен вычислительной нагрузке.** Важно учитывать CPU-время одной проверки и параллелизм.
2. **Кэшировать можно не только данные, но и результаты вычислений.** Это особенно полезно для CPU-heavy систем.
3. **Rate limiting стоит применять до дорогой обработки.**
4. **CPU и RAM нужно рассчитывать отдельно.** Количество хостов определяет наиболее жёсткое ограничение.
5. **Запуск чужого кода требует изоляции.** Контейнер — лишь часть решения.
6. **Разделение кода и метаданных** позволяет хранить файлы решений в S3-like storage, а сведения о них — в PostgreSQL.
